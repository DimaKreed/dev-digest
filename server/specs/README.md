# server/specs

The intended behavior of a feature, written **before** it is implemented, then kept as the
acceptance reference.

Convention: one file per feature, `NN-feature-name.md`. Write it, get it agreed, then build
against it. When behavior changes, update the spec in the same change — a stale spec is
worse than none.

A spec covers: the endpoints/contracts involved, the states and transitions, error and edge
cases, and what "done" means. It does not cover implementation structure — that's the code,
and the reasoning behind it goes in [../docs/](../docs/).
